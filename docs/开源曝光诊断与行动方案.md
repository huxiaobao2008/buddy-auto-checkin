## 二、为什么没人发现（按影响力排序）

### 1. 15 天零提交，看起来像废弃项目 —— 已修复 ✅
`createdAt 2026-10-05T22:12:49Z`，`pushedAt 2026-10-05T22:12:58Z`，两者相差 **9 秒**，
意味着建仓即推送，此后再无更新。GitHub 的搜索排序与 Trending 都偏好有近期活动的仓库，
一个 15 天没动的仓库既排不上 Trending，访客看到"最后一次提交=建仓那天"也会直接关掉。
→ 已于 2026-10-20 02:28 推送 2 个提交（积分台账 + README 升级），`pushedAt` 已刷新。

### 2. 零社交证明，马太效应反噬 —— 待解决 ⚠️
Star 数是最强的可见信号：0 star 的仓库，即便内容扎实，陌生人也会默认"没人验证过=不敢用"；
反之 1429 star 的竞品会被默认"可靠"。这是**鸡生蛋问题**，靠 GitHub 内部自然流量破不了。

### 3. 首屏没有钩子，扫一眼就走 —— 已修复 ✅
原 README 开头是 3 行中文描述 + 安全须知，没有 badges、没有能力列表、没有截图位，
访客需要读完才能判断"这东西对我有什么用"。多数人不会读。
→ 已加 badges、英文摘要、「一眼看懂」能力速览表、同类对比、FAQ。

### 4. 缺「AI 一句话安装」路径 —— 最关键的结构性缺失 🔴
这是竞品能火的核心机制，我们完全没有。见下一节。

### 5. 搜索赛道拥挤且已固化 —— 结构性劣势
关键词 `workbuddy` 下 GitHub 有 **6693** 个仓库，头部被 1000+ star 项目占满
（`linguo2625469/workbuddy2api-panel` 4022、`AlephAITech/WorkBuddyGuide` 3527、
`88lin/workbuddy-auto-signin` 1429）。默认排序下新仓库沉在几十页之后，
**不可能靠 GitHub 搜索获得自然流量**。

## 三、竞品是怎么被发现的（一手证据）

| 竞品 | Star | 传播机制（原文实证） |
|---|---:|---|
| `88lin/workbuddy-auto-signin` | 1429 | **README 是写给 AI 看的**。用户把仓库链接丢给 AI 助手说一句"帮我装好，设成每天定时签到"，AI 自己完成 clone、建 launchd/计划任务、跑验证。博主原文："我在旁边插不上手"。传播路径：Obsidian 交流群转发 → 个人博客详解 → 技术社区收录 |
| `liubinne/workbuddy-free-credits` | — | 同样主打"一句话安装"，被**微信公众号**与**今日头条**文章写成教程（原文给出可直接复制给 AI 的完整提示词） |
| `lk610322lk-creator/workbuddy-cloud-checkin` | — | 做成 **SKILL.md 技能包**形态，可直接 `git clone` 到 `~/.workbuddy/skills/` 下即用，自带中文菜单 Start.bat |

**共同规律（这是本次调研最有价值的发现）：**

1. 它们的流量**不来自 GitHub 搜索**，而来自**内容平台种草**（公众号、头条、个人博客、技术社区、微信群）。
2. 它们把**安装成本降到一句话**——README 面向 AI 而非面向人，用户不需要理解项目就能用上。
3. 单文件 / 零依赖 / 技能包形态，上手门槛极低。
4. 每篇传播文章都主动做**安全审计背书**（"无外传、凭证不落盘、已逐行审计"），消除首次信任障碍。

对照本项目：1.7 万行多模块、必须 Windows + 客户端在线、安装要 5 步命令、README 面向人。
**内容不差，但"让人用上"的路径太长。**

## 五、风险提示（发布前必读）

1. **多账号是争议点**：两个同类项目在文档中明确反对"多账号薅取"。
   对外表述统一为「多账号**统一管理**工具，用于管理本人名下账号」，不要出现"批量薅"字样。
   README 与 INSTALL_PROMPT 已按此口径撰写。
2. **每次推送前确认脱敏**：`accounts/`、`config.json`、`logs/`、`data/` 已被 `.gitignore` 忽略，
   已核验 74 个入库文件中无敏感路径。发布前可跑 `python tools/build_opensource.py` 复核。
3. **接口来自逆向**：与所有同类项目一致，需声明"非官方、接口可能随时变动"。
