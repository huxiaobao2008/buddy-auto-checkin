二、真实业务需求提取

需求来源为项目内docs/ 三份文档与代码实现双向验证，非主观推测。

2.1 产品定位

WorkBuddy 多账号无人值守自动化工具：完全模拟真人操作路径，自动完成每日签到、19 个成长任务、积分领取全流程，不触发风控。用户仅需启动后点击执行，全程无需人工干预。

2.2 功能边界

维度边界内容来源依据
执行粒度三档：一键全自动 / 单账号 / 单任务重跑WORKFLOW.md 第二节
账号范围仅遍历 config.json 中 enabled=true 的账号run_all.py:266
任务分类已完成→跳过；需扫码/付费/无积分→人工跳过；其余→执行PROJECT-REQUIREMENTS 三.6
客户端依赖API 阶段不依赖客户端；UI 阶段不可达则整段跳过run_all.py:472
临时内容必须等服务端确认积分到账后才可删除PROJECT-REQUIREMENTS 三.5

2.3 六条执行铁律

1 · 串行铁则

单客户端严格串行，验证会话真的创建、任务已开始执行后才操作下一个，绝对不并发。

2 · 发射即走

确认发起成功立刻进入下一个，不等 AI 完整回复、不等报告生成。

3 · 切号唯一标准

所有任务计分 + 积分到账后才切号，禁止按固定时间预算强制切走。

4 · 无固定等待

不写死 sleep 时间，只判断元素加载与服务端进度更新。

5 · 删除规则

临时创建的定时任务、会话，拿到积分前绝对不删除。

6 · 初始判断

先拉服务端进度，已完成任务直接标记跳过，不提前硬编码跳过项。

三、五层架构关系

系统采用分层架构，各模块职责单一、不跨层写逻辑，便于维护与验证。

① 入口与调度层

auto_buddy.py · launcher.py · client_cdp.py · 一键启动脚本

拉起带 CDP 9222 调试端口的客户端并管理生命周期，启动本地 Web 服务，提供命令行与一键启动入口。

② 编排调度层

orchestrator/ · run_all.py · batch.py · claim.py · adaptive.py

两阶段顺序调度、账号遍历与切号、任务分类标记、统一复核补做、统一积分领取、断点续传、全局停止标记。本次修复的日志统一出口 p(stage, msg) 位于此层。

③ 执行引擎层

engine/ · missions/ · core/

driver.py 做 CDP 会话管理与原子 UI 操作；missions_api.py 封装服务端接口流水线；missions/ 按场景拆分 chat、team、panels、experts；core/ 提供配置、凭证、DOM 等基础能力。所有操作自带状态校验。

④ Web 控制台层

web/ · server.py · ui.html

本地 HTTP 服务提供状态快照与 action 分发，子进程托管不阻塞服务；前端工作台与执行控制台分开展示 API / UI 双区域日志。本次修复的日志解析与状态判定位于此层。

⑤ 数据与配置层

config.json · accounts/ · data/ · logs/ · docs/

全局配置、加密凭证、模板与专家去重账本、运行状态、结构化日志与证据快照。所有数据可追溯，不丢状态。

架构层面的核心修复

新增 core/logproto.py 作为日志格式的唯一事实来源，由第②③④ 层共同引用。此前格式定义散落在三处，任何一处改动都会让前后端静默失配。

五、问题清单与修复

P0-1日志分流全面失效（单账号 / 单任务路径）
位置
web/server.py → _run_account_job()、_run_ui_code_job()
现象
单账号与单任务执行时，API 阶段日志显示在 UI 区域，API 区显示「暂无日志」
根因
两处硬编码 "[%s][ui:%s] %s" % (CFG.now_str(), key, m)。now_str() 返回 2026-10-02 17:07:02，而行首是 2026- 而非两位小时，整批日志与正则失配且不报任何错；同时 area 硬编码为 ui，即使匹配成功也会错投
修复
新增 core/logproto.py；两处改用 LP.format_line()，并以 _infer_area() 按内容关键词归类到 API / claim / UI
验证
回归测试断言时间戳可被前端正则解析；端到端验证 8 行日志 100% 唯一归类
P0-2已完成任务被误判为「已停止」
位置
web/server.py → run_all_status()
现象
正常跑完的任务，工作台显示「已停止」
根因
判定逻辑为「最后 10 行含『停止』二字即视为已停止」。而正常收尾日志中同样可能出现该词（如「本轮不停止，正常执行」），属典型的关键词猜测状态
修复
改为按行首 area 判定归属，从后往前遍历，遇到完成标记立即判定为正常结束（完成优先级高于停止）；仅接受「收到停止指令」「中止」等明确信号
验证
回归测试含专门用例：正文含停止字样 + 完成收尾 → 判定为未停止，同时验证旧逻辑在该用例上会失败
P1-3日志文件句柄泄漏
位置
web/server.py → action_run_all()
现象
反复执行后日志文件无法打开，Windows 报权限拒绝
根因
RUN_ALL_LOG 全局句柄保存后从未关闭；重开时未先 close 旧句柄。Windows 上未关闭句柄会锁住文件，导致本轮 truncate(0) 失败
修复
重开前先 close 并置空，关闭操作包 try except 保证失败不阻断主流程
P1-4action_stop 可能抛 AttributeError
位置
web/server.py → action_stop()
现象
点击停止时接口返回 500，停止标记已写但前端无反馈
根因
等待循环中直接调用 RUN_ALL_PROC.poll() 未判空，进程对象失效即抛异常；原代码还有嵌套的重复 if 判断，逻辑冗余且存在竞态
修复
提取局部变量并逐次判空；补充单任务（UI_CODE_JOB）停止处理，原先该路径完全无法停止
P1-5UI 阶段识别在跳过分支下误判
位置
web/ui.html → renderConsole()
现象
所有账号 UI 任务都已完成时，界面仍显示「正在跑 API 阶段」
根因
hasUiPhase = /\[ui:/.test(tail)，而「已完成账号跳过 UI 驱动」与「客户端未就绪跳过 UI」两条分支根本不产生 [ui: 前缀行
修复
改为扫描行首受控 area 标记 ^\[\d{2}:\d{2}:\d{2}\]\[ui[:\]]
P2-6账号轨道错乱（旧兜底分支重复切换账号）
位置
web/ui.html → parseAccountPipe()
现象
账号列表重复出现，进度归属错误
根因
新旧两条分支共存——新协议分支已处理账号切换，末尾还有一条无锚点正则 \[(?:ui|api):([a-z0-9_]+) 会再次切换当前账号
修复
删除已被覆盖的兜底分支，「接取/领取」阶段解析合并入新协议分支
P2-7账号列表解析易被中文标点截断
位置
web/ui.html → parseAccountPipe()
现象
启动日志已打印账号列表，前端轨道仍为空
根因
正则 启用账号\s+\d+\s+个[:：]\s*([a-z0-9_,\s]+) 字符类含 \s 且要求整段连续，遇到中文标点即截断失败
修复
改为全局提取 account_[a-z0-9_]+ 并去重
P2-8重复函数定义
位置
web/server.py → action_run_account()
现象
连续两行相同 docstring
修复
删除重复行
