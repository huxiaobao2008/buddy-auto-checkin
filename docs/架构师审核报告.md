# 架构师视角：项目完整审核报告

> 审核对象：`D:\workbuddy自动签到领积分完成成长任务`（最新版，唯一基准）
> 审核日期：2026-10-02
> 审核方式：读全部 UI 交互代码 + 全部 17 个后端接口 + 需求铁则逐条对照
> 审核结论：**发现 1 个架构性缺陷（串行铁则形同虚设），5 个功能缺陷**

## 第一部分：现在 UI 有哪些功能（大白话）

界面共 **4 个页面**、**17 个后端接口**，全部功能如下。

### 页面一：总览仪表盘（dashboard）

打开工作台第一眼看到的，就是这个页面。

| 显示内容 | 从哪来 | 刷新方式 |
|---|---|---|
| 20 个账号今天签到几个 | 服务端 | 每 2 秒静默刷新 |
| 累计多少积分、还剩多少 | 服务端 | 同上 |
| 待领积分多少 | 服务端 | 同上 |
| 客户端是否在线 | CDP 探测 | 同上 |
| 定时执行规则 | 本地配置 | 同上 |

**一句话**：像手机银行的首页，看钱和状态，**不操作**。

### 页面二：账号管理（accounts）

20 个账号的清单，每个账号能做 8 件事：

| 功能 | 按钮 | 实际干什么 |
|---|---|---|
| 启用/停用 | 开关 | 改配置，决定是否参与自动执行 |
| 执行本账号 | 「执行」 | 只跑这一个账号的完整流程 |
| 切到这个账号 | 点账号卡 | **把客户端登录切成这个账号** |
| 接取任务 | 任务行按钮 | 调服务端接口接任务 |
| 领取积分 | 任务行按钮 | 调服务端接口领积分 |
| 单跑一个 UI 任务 | 任务行「执行」 | 只跑这一个任务 |
| 登录/续期 | 按钮 | 重新抓登录态 |
| 删除账号 | × | 从配置移除 |

### 页面三：执行控制台（console）

真正干活的地方，分两栏：

- **左栏 API 日志**：显示签到、领积分、热度这些**不用点鼠标**的操作日志
- **右栏 UI 日志**：显示模板、专家、资料库这些**要动鼠标**的操作日志
- **顶部状态**：当前跑的是「一键全自动 / 本账号 / 单任务」，运行中/已完成/已停止

### 页面四：发现账号（discovered）

扫描客户端登录目录，把找到的账号列出来，可以「添加」到配置里。

### 全局功能（4 个页面都能看到）

- **手动 / 自动模式切换**（顶部）
- **⚡ 一键全自动**（跑全部 20 个账号）
- **■ 停止任务**
- 恢复主号

## 第二部分：完整执行逻辑（一步步讲）

### 「一键全自动」点下去发生了什么

```
① 前端检查：runAllTimer/uiCodeJobTimer/acctJobTimer 有没有一个在跑
   → 有就直接弹「已有任务进行中」并 return（JS 侧拦截）

② 后端 action_run_all：
   - 检查 RUN_ALL_PROC 是否还活着 → 活着就返回「已在运行中」
   - 清掉旧的停止标记
   - 打开日志文件（把上次的日志清空）
   - 启动一个【独立子进程】跑 run_all()，日志写进那个文件

③ 子进程里 run_all() 依次做：
   a. 读配置，取出 20 个 enabled 的账号
   b. 读 progress.json，跳过今天已完成的账号（断点续传）
   c. 检查客户端 CDP 端口 9222 通不通
      → 不通就只跑 API 阶段，UI 阶段整个跳过
   d. 【阶段一 API】20 个账号挨个跑：
      签到 → 领Buddy → 开盲盒 → 派猫猫 → 出行奖励 → 伙伴状态 → 热度 → 接任务
      每次都先问服务端「这个做了没」，做了就跳过
   e. 【阶段二 UI】20 个账号挨个来，每个账号：
      切号 → 拉 19 个任务清单 → 分类（已完成/需人工/待做）
      → 逐个串行做任务（模板、专家、专家团、资料库、面板…）
      → 每个任务确认「会话真的创建了」才走下一个
      → 全部做完才切下一个账号
   f. 【阶段三 收尾】把「待领取」的积分全领了
   g. 切回启动前那个账号

④ 前端每 2 秒轮询 /api/state，把日志和状态显示出来
```

### 「单任务执行」点下去发生了什么

```
前端：检查有没有别的任务在跑 → POST /api/run-ui-code {key, code}
后端：
  - 查 key 和 code 合法性
  - 如果 UI_CODE_JOB 在跑：写停止标记，等它退出（最多 30 秒）
  - 置位 running=True
  - 起线程跑 _run_ui_code_job
线程里：切号 → 只做这一个任务 → 领积分 → 切回原账号
```

## 第三部分：找到的问题（架构级，按严重程度）

### 【致命】问题 1：串行铁则实际上没有任何机制在保证

**需求原文**：
> 单客户端仅支持串行操作……绝对不并行、不批量并发，避免页面混乱、找不到入口。

**大白话解释**：
这个需求的意思是——**同一时间只能有一个人在操作 WorkBuddy 客户端**。
像做饭一样，不能两个人同时用同一个灶台，会打架。

**现在实际是什么样**：

我扫了所有入口，**没有任何一个地方检查"别的任务在不在跑"**：

| 入口 | 检查了谁 | 漏了谁 |
|---|---|---|
| 一键全自动 | 只看 `RUN_ALL_PROC` | 单账号任务、单任务、**手动切号** |
| 单账号 | 只看 `ACCT_JOB` | 全自动、单任务、**手动切号** |
| 单任务 | 只看 `UI_CODE_JOB` | 全自动、单账号、**手动切号** |
| **手动切号** | **什么都没检查** | 全部 |
| 接取/领取任务 | 只看 `T.SERIAL_LOCK` | 全部 UI 任务 |

**最危险的场景（大白话）**：

一键全自动正在跑，第 8 个账号切过去、正在做"使用5个模板"任务。
这时候你在页面上手贱，点了另一个账号的「切到这个账号」。

结果：
1. 手动切号把客户端登录态改了
2. 自动任务**还在这个账号的流程里**，它不知道登录态变了
3. 它继续做模板任务 → **任务实际做到了别的账号头上**
4. 积分记错账号

**为什么我前两次"修复"都没修好**：
因为我一直在给每个入口单独加锁。但问题不在"某个入口有 bug"，
而在于**整个项目从来没有"客户端被占用"这个概念**。
我加的锁只能防住"双击同一个按钮"，防不住"任务跑到一半手动切号"。

更糟的是——**这层保护在 UI 上看起来是有的**：
```javascript
if (runAllTimer || uiCodeJobTimer || acctJobTimer){ toast('已有任务进行中'); return; }
```
前端 JS 里确实检查了。但这是**浏览器里的变量**，只防住同一个浏览器页面。
后端 `action_client_switch` 压根没检查，而且**手动切号按钮在账号页，点的时候不会经过那个 JS 检查**。

**结论**：串行铁则目前只在一半场景生效（前端单页面双击），后端完全裸奔。

---

### 【严重】问题 2：切号接口在持有全局锁的情况下做 6 秒验证

**大白话**：`action_client_switch` 拿着那把全局锁，去做一件要 6 秒的事（等客户端界面昵称变成新账号）。

**后果**：这 6 秒里，**整个 Web 服务所有接口都被阻塞**——状态轮询卡住、停止按钮点不动、页面转圈。

**为什么是设计错误**：锁应该只保护"改数据"的那一瞬间，不该覆盖"等待外部响应"的漫长过程。
这是把"互斥"误用成了"串行化一切"。

---

### 【中】问题 3：前端读错了后端字段名，单任务状态永远显示不出来

- 后端产出：`uicode_job`
- 前端读：`STATE.ui_code_job`（多了个下划线）

**后果**：你点单任务执行，**日志区一片空白**，看不到任何输出。
但后端其实在正常跑、日志也在正常写——只是前端拿不到数据。

我已在上轮修掉，但说明**这类"字段名对不上"的问题没有任何机制能提前发现**。

---

### 【中】问题 4：接口契约没有校验手段

后端注册了 17 个接口，前端用其中 16 个。
如果哪天有人改了后端字段名，**没有任何测试会失败**，只能靠人眼发现。

---

### 【轻】问题 5：前端的"已有任务"检查形同虚设

```javascript
if (runAllTimer || uiCodeJobTimer || acctJobTimer)
```
这三个变量是**页面加载后由 JS 定时器创建的**。意味着：
- 刷新页面后，变量丢失 → 检查失效
- 直接调后端接口（curl/其他工具）→ 根本不经过

**它是安慰剂，不是防线。**

## 第四部分：解决方案（为什么这么设计）

### 核心思路：把"客户端占用"变成一个真实存在的东西

**大白话**：现在的问题是"谁在用灶台"这个信息**根本不存在**，大家只能各自猜。
解法是**在厨房门口挂个牌子**，谁要用先把牌子翻过来，别人看到就等着。

### 方案 A：引入「客户端占用令牌」（根治，推荐）

**新增 `core/client_lock.py`，全项目唯一入口：**

```
try_acquire(kind, key)  →  抢到牌子才能开始干活
release(kind, key)      →  干完活翻回牌子（finally 保证一定归还）
holder()                →  现在牌子在谁手上
```

**改造 4 个地方：**

1. **四个入口统一抢同一块牌子**
   - `run_all` / `run_account` / `run_ui_code` / `client_switch` 全部调用 `try_acquire`
   - 抢不到就返回明确错误："XX 正在执行中，请等待"
   - 删掉各自的那套 `_RUN_ALL_STARTING`、`ACCT_JOB["running"]` 判断

2. **切号是破坏性操作，必须在牌子上**
   - `switch_to()` 内部加断言：没持有牌子不让切
   - 这是**兜底**：将来新增任何入口忘了加守卫，也不会切错号

3. **牌子要跨进程**
   - `run_all` 是独立子进程，Python 的 `threading.Lock` 对它无效
   - 需要文件锁（`os.open` + `O_EXCL` 原子创建，或 `msvcrt.locking`）
   - 保证 Web 进程和子进程之间也互斥

4. **牌子状态要暴露给 UI**
   - `/api/state` 返回 `holder`，前端显示"当前被 主号·邻家·使用5个模板 占用"
   - 用户冲突时看得见原因，而不是只看到"已启动"

**为什么这是根治不是补丁**：

| | 现在的补丁 | 令牌方案 |
|---|---|---|
| 状态存几处 | 4 处（RUN_ALL_PROC + 3 个 JOB 字典） | **1 处** |
| 新增入口要做什么 | 记得复制粘贴检查逻辑，漏了就出 bug | 调 `try_acquire`，漏了也有底层断言兜底 |
| 跨进程有效吗 | ❌ threading.Lock 不行 | ✅ 文件锁 |
| 我前两次的问题 | 加了标志位还是漏 | — |

### 方案 B：切号锁范围收窄（配套，必须做）

把 `action_client_switch` 里的 `with LOCK` **只包住状态更新那几行**，
切号本身放在锁外，用令牌代替锁来做互斥。

**理由**：锁保护的是"内存数据"，切号是"等外部响应"，两者时间尺度差了几个数量级。

## 第五部分：执行步骤（如果实施，按这个顺序）

| 步骤 | 做什么 | 为什么这个顺序 | 验证方式 |
|---|---|---|---|
| 1 | 新建 `core/client_lock.py` | 先有基础件才能改造 | 单测：同进程抢两次，第二次必失败 |
| 2 | 加文件锁支持跨进程 | run_all 是子进程，必须先支持 | 起了子进程占牌，主进程抢不到 |
| 3 | 改 `action_run_all` | 最危险的（自动跑着被人切号） | 并发请求测试：跑着时切号被拒 |
| 4 | 改 `action_run_account` | 第二个入口 | 同上 |
| 5 | 改 `action_run_ui_code` | 第三个入口 | 同上 |
| 6 | 改 `action_client_switch` + 收窄锁范围 | 补最后缺口 + 解决阻塞 | 切号时其他接口不卡 |
| 7 | `switch_to()` 加底层断言 | 纵深防御 | 无令牌时切号抛错 |
| 8 | `/api/state` 暴露 holder | 让冲突可见 | 接口返回 holder 字段 |
| 9 | 前端显示 holder | 用户能看懂为什么被拒 | 页面显示占用者 |
| 10 | 删掉 4 处旧的状态判断 | 收尾，避免两套并存 | 代码审查无残留 |
| 11 | 端到端并发验证 | 证明真修好了 | 真起服务，10 个并发请求，只放行 1 个 |
| 12 | 加契约测试 | 防字段名再对不上 | 后端产出键 ⊇ 前端引用键 |

## 第六部分：风险与遗留

| 风险 | 说明 | 应对 |
|---|---|---|
| 子进程崩溃后牌子不归还 | 文件锁残留 | 用 PID + 时间戳，读取时判断进程是否存活 |
| 令牌被长期持有不释放 | 页面永远显示占用中 | 加最大持有时长（如 2 小时）超时强制释放 |
| 改动涉及编排层 | run_all/batch 入口要改令牌传递 | 分步验证，每步可独立回滚 |
| 现有 `SERIAL_LOCK` 怎么办 | 与令牌职责重叠 | 保留但降级为"任务接口内部串行"，令牌管"客户端全局独占" |

**未覆盖场景（诚实说明）**：
- 客户端崩溃重连时的令牌状态
- 跨机器/远程访问（当前只监听本机，风险低）
- 真正的 UI 自动化执行（本轮只验证到"任务正确启动并被正确拒绝"，未跑完整 20 账号全流程）
