## 一、真实业务需求提取（来源：项目文档 + 代码实现双向验证）

### 1.1 产品定位
WorkBuddy 多账号无人值守自动化工具：模拟真人操作路径，自动完成每日签到、
19 个成长任务、积分领取全流程，不触发风控。用户仅需启动后点击执行。

### 1.2 功能边界

| 边界 | 内容 | 来源 |
|---|---|---|
| 执行粒度 | 三档：一键全自动 / 单账号 / 单任务重跑 | WORKFLOW.md 第二节 |
| 账号范围 | 仅遍历 `config.json` 中 `enabled=true` 的账号 | `run_all.py:266` |
| 任务分类 | 服务端已完成→跳过；需扫码/付费/无积分→人工跳过；其余→执行 | PROJECT-REQUIREMENTS 三.6 |
| 客户端依赖 | API 阶段不依赖客户端；UI 阶段客户端不可达则整段跳过 | `run_all.py:472` |
| 临时内容 | 必须等服务端确认积分到账后才删除 | PROJECT-REQUIREMENTS 三.5 |

### 1.3 六条执行铁律（不可违反）
1. **串行铁则**：单客户端严格串行，验证会话创建后才操作下一个，禁止并发
2. **发射即走**：确认发起成功立刻进入下一个，不等 AI 完整回复
3. **切号唯一标准**：所有任务计分 + 积分到账后才切号，禁止按时间预算强切
4. **状态判断**：不写死固定等待，只判断元素加载与服务端进度
5. **删除规则**：临时内容拿到积分后才删
6. **初始判断**：先拉服务端进度，已完成直接跳过

### 1.4 技术约束（代码中真实存在的硬性限制）
- **零第三方依赖**：Web 层仅用标准库 `http.server`，无 Web 框架
- **仅监听 127.0.0.1**：不对外暴露，响应不含 token
- **无固定等待**：不写死 sleep 时间预算，基于元素/服务端状态判断
- **日志分流**：API / UI 日志独立，前端分开展示，只读本次执行日志
- **token 脱敏**：`config.mask()` 保证任何输出不含完整 token

## 二、问题清单

### P0-1 日志分流全面失效（单账号 / 单任务路径）

- **位置**：`web/server.py:_run_account_job()`、`web/server.py:_run_ui_code_job()`
- **现象**：单账号与单任务执行时，API 阶段日志被显示在 UI 区域，API 区域显示「暂无日志」
- **根因**：两处均硬编码 `line = "[%s][ui:%s] %s" % (CFG.now_str(), key, m)`
  - `CFG.now_str()` 返回 `2026-10-02 17:07:02`，而前端正则要求 `^\[\d{2}:\d{2}:\d{2}\]`
  - 行首是 `2026-` 而非两位小时，**整批日志失配**，且不报错，只是全部落入兜底分支
  - area 硬编码为 `ui`，即使匹配成功，API 阶段日志也会被错投到 UI 区
- **影响**：用户无法区分 API 与 UI 阶段进度，排障时方向全错
- **修复**：新增 `core/logproto.py` 统一协议；两处改用 `LP.format_line()` + `_infer_area()` 按内容归类
- **验证**：`tests/test_logproto.py` 断言时间戳可被前端正则解析

### P0-2 已完成任务被误判为「已停止」

- **位置**：`web/server.py:run_all_status()`
- **现象**：正常跑完的任务，工作台显示「已停止」
- **根因**：判定逻辑为「最后 10 行含『停止』二字即视为已停止」。
  而正常收尾日志中同样可能出现该词（如「本轮不停止，正常执行」）
- **影响**：用户误以为任务失败，可能重复执行已完成任务
- **修复**：改为按行首 area 判定归属，**完成标记优先级高于停止标记**，
  从后往前遍历时遇到完成标记立即判定为正常结束
- **验证**：回归测试含专门用例「正文含停止字样 + 完成收尾 → 判定为未停止」

### P1-3 日志文件句柄泄漏

- **位置**：`web/server.py:action_run_all()`
- **现象**：反复执行后日志文件无法打开，Windows 报权限拒绝
- **根因**：`RUN_ALL_LOG` 全局句柄保存后从未关闭；重开时未先close 旧句柄。
  Windows 上未关闭的句柄会锁住文件，导致本轮 `truncate(0)` 失败
- **影响**：长时间使用后任务无法启动
- **修复**：重开前先 close 并置空；关闭操作包 try except，失败不阻断主流程

### P1-4 `action_stop` 可能抛 AttributeError

- **位置**：`web/server.py:action_stop()`
- **现象**：点击停止时接口返回 500，停止标记写了但前端无反馈
- **根因**：等待循环中直接调用 `RUN_ALL_PROC.poll()`，未判空。
  原代码还有嵌套的重复 `if` 判断，逻辑冗余且存在竞态
- **影响**：用户点了停止但不知是否生效
- **修复**：提取局部变量 `proc` 并逐次判空；补充单任务（UI_CODE_JOB）停止处理

### P1-5 UI 阶段识别在跳过分支下误判

- **位置**：`web/ui.html:renderConsole()`
- **现象**：所有账号 UI 任务都已完成时，界面仍显示「正在跑 API 阶段」
- **根因**：`hasUiPhase = /\[ui:/.test(tail)`，而「已完成账号跳过 UI 驱动」
  与「客户端未就绪跳过 UI」两条分支根本不产生 `[ui:` 前缀行
- **影响**：进度条停在错误阶段
- **修复**：改为扫描行首受控 area 标记 `^\[\d{2}:\d{2}:\d{2}\]\[ui[:\]]`

### P2-6 账号轨道错乱（旧兜底分支重复切换账号）

- **位置**：`web/ui.html:parseAccountPipe()`
- **现象**：账号列表重复出现，进度归属错误
- **根因**：新旧两条分支共存 —— 新协议分支已处理账号切换，
  末尾还有一条无锚点正则 `\[(?:ui|api):([a-z0-9_]+)` 会再次切换当前账号
- **修复**：删除已被覆盖的兜底分支，「接取/领取」阶段解析合并入新分支

### P2-7 账号列表解析易被中文标点截断

- **位置**：`web/ui.html:parseAccountPipe()`
- **现象**：启动日志已打印账号列表，前端轨道仍为空
- **根因**：正则 `启用账号\s+\d+\s+个[:：]\s*([a-z0-9_,\s]+)` 字符类含 `\s`
  且要求整段连续，遇到中文标点即截断失败
- **修复**：改为全局提取 `account_[a-z0-9_]+` 并去重

### P2-8 重复函数定义

- **位置**：`web/server.py:action_run_account()`
- **现象**：连续两行相同 docstring
- **修复**：删除重复行
