# 日志协议设计原则与故障模式

> 全部内容来自真实项目治理过程（WorkBuddy 多账号自动化工程），
> 每条故障均给出「症状 → 根因 → 判据 → 修复」四段式，可直接复用。

## 一、协议设计三原则

### 原则 1 · 单一事实来源
格式定义**只能存在一处**。任何第二处拼装都是缺陷，无论它当前是否正确。

真实案例：同一工程中，三条日志路径各自拼装前缀：

| 路径 | 原实现 | 问题 |
|---|---|---|
| 编排层 | `"[%s][%s] %s" % (strftime("%H:%M:%S"), stage, msg)` | 正常 |
| 单账号 | `"[%s][ui:%s] %s" % (now_str(), key, m)` | 时间戳精度不同、area 硬编码 |
| 单任务 | `"[%s][ui:%s] %s" % (now_str(), key, m)` | 同上 |

其中 `now_str()` 返回 `2026-10-02 17:07:02`，而前端正则要求
`^\[\d{2}:\d{2}:\d{2}\]`。**行首是 `2026-` 而非两位小时，整批日志失配**，
且不报任何错，只是全部落进兜底分支。

### 原则 2 · 受控枚举，拒绝自由文本
area 必须来自固定集合。自由文本的 area 会让解析侧无法建立完备分支，
新增一个 area 就可能悄悄破坏既有分流。

落地做法：定义 `VALID_AREAS` 集合，未知值统一降级为 `start`
（而非抛异常——日志不能因格式问题中断业务）。

### 原则 3 · 解析必须行首锚定
`line.includes("阶段二")` 这类无锚点判断，会把正文中间出现的同名字样
也当成阶段标记。真实案例中「本轮不停止，正常执行」这句话里的
「停止」二字曾导致已完成任务被误判为已停止。

正确做法：`/^\[\d{2}:\d{2}:\d{2}\]\[ui[:\]]/m`。

## 二、日志行格式规范

统一三段式：

```
[HH:MM:SS][<area>:<account_key>] <message>
```

- 时间戳只用 `HH:MM:SS`，精度在协议模块内唯一确定
- area 受控，取值集合与前端声明**逐一对应**
- account 可为空，此时省略冒号部分
- 账号标识仅接受 `account_` 前缀形态，其他形态丢弃，防止污染账号轨道

### area 与前端区域的映射

| area | 归属区域 | 语义 |
|---|---|---|
| `start` | API侧 | 启动、断点续传、总览 |
| `client` | API 侧 | 客户端与 CDP 生命周期 |
| `api` | API 侧 | 阶段一纯接口管线 |
| `claim` | API 侧 | 阶段三收尾领取 |
| `order` | API 侧 | 排序与计划 |
| `ui` | UI 侧 | 阶段二 UI 管线 |
| `done` | UI 侧 | 收尾汇总 |
| `report` | UI 侧 | 报告输出 |

**该映射必须在后端与前端各声明一次且保持一致**，并由测试断言两侧集合相等。

## 三、故障模式清单（含真实判据）

### FM-1 日志分流失效
- **症状**：所有日志出现在同一区域，另一区域显示「暂无日志」
- **根因**：写入端与解析端格式不一致；或解析正则缺行首锚定
- **判据**：构造协议产出行，断言能被解析正则匹配；断言 API 桶不含 ui 行
- **修复**：统一到协议模块；正则加 `^` 锚定
- **验证**：回归测试须含真实阶段序列用例，断言两桶行数正确

### FM-2 状态误判
- **症状**：正常完成的任务显示「已停止」
- **根因**：用关键词猜测状态。原实现判断最后 10 行是否含「停止」，
  而正常收尾日志中同样可能出现该词
- **判据**：构造「正文含停止字样且以完成标记收尾」的用例，结果必须为未停止
- **修复**：按行首 area 判定归属，**完成标记优先级高于停止标记**，
  从后往前遍历时遇到完成标记立即判定为正常结束

### FM-3 句柄泄漏
- **症状**：反复执行后日志文件无法打开；Windows 报权限拒绝
- **根因**：重新打开前未关闭上一轮句柄
- **判据**：连续执行 N 次后句柄数不增长
- **修复**：重开前先 close 并置空；关闭操作包 try except，失败不阻断主流程

### FM-4 账号轨道错乱
- **症状**：账号列表重复、进度归属错误
- **根因**：无锚点正则 `\[(?:ui|api):([a-z0-9_]+)` 误捕正文内容；
  且新协议分支与旧兜底分支共存导致重复切换当前账号
- **判据**：断言解析出的账号序列与写入顺序一致
- **修复**：行首锚定加显式捕获组；删除已被覆盖的兜底分支

### FM-5 账号列表解析失败
- **症状**：启动日志已打印账号列表，前端轨道仍为空
- **根因**：原正则 `启用账号\s+\d+\s+个[:：]\s*([a-z0-9_,\s]+)`
  的字符类含 `\s` 且要求整段连续，遇到中文标点即截断
- **判据**：断言能从混合文本中提取全部 `account_` 标识
- **修复**：改用全局提取 `account_[a-z0-9_]+` 并去重

## 四、迁移 checklist

- [ ] 列出全部写入点与解析点，建立一一对应映射
- [ ] 新建协议模块，定义受控枚举与三个核心函数
- [ ] 迁移写入点，确认业务代码中时间戳拼装归零
- [ ] 迁移解析点，全部正则行首锚定
- [ ] 加固状态判定，完成标记优先
- [ ] 治理句柄生命周期
- [ ] 编写回归测试，镜像解析侧正则
- [ ] 测试须包含至少一个旧逻辑会失败的用例
- [ ] 两工程/多副本同步修复，避免版本漂移

## 五、反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 每条路径各自拼前缀 | 格式漂移，静默失效 | 统一协议模块 |
| 正则不锚定行首 | 误捕正文 | 加 `^` 锚定 |
| 用关键词判断状态 | 误判 | 按结构化 area 判定 |
| 无枚举的 area | 分流不完备 | 受控集合加降级 |
| 日志格式校验抛异常 | 业务中断 | 降级为默认值 |
| 只测正常路径 | 漏掉误判类缺陷 | 必测旧逻辑会失败的用例 |
| 覆盖式同步多副本 | 抹掉历史差异 | 精准移植改动 |
