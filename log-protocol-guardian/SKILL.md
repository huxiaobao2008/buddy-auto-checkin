# 日志协议守护

把「日志怎么写」与「日志怎么读」收敛为一份可执行契约，并用测试锁死。

## 一、职责与边界

- 做：
  1. 抽取日志行格式为独立协议模块（唯一事实来源）
  2. 迁移所有写入点与解析点，消除各自硬编码的正则
  3. 建立回归测试，验证「后端产出的行能被解析侧正则正确解析」
  4. 修复由格式不一致衍生的状态误判、串区、句柄泄漏
- 不做：
  - 不改造与日志协议无关的业务逻辑
  - 不引入第三方日志库或结构化日志框架，保持零依赖
  - 不处理日志内容本身的业务语义校验

## 二、为什么需要它（可验证的差异）

日志串区与误判的根因不是正则写错，而是同一份格式在多处各写一遍。
一旦某条路径改了时间戳精度或漏了前缀，解析侧立刻失效且无任何报错——
日志只是安静地全部落进兜底分支。

| 对标基准 | 本技能的差异 |
|---|---|
| 人工 review 逐个核对格式 | 回归测试自动断言前后端正则一致，纳入版本管理 |
| 统一改用 logging 加 JSON handler | 零依赖纯文本协议，兼容现有前端 textContent 渲染 |
| 出问题后加日志排查 | 协议层校验失败即拦截，问题在写入点暴露而非显示端 |

核心判据：任意一条日志行，都能被解析侧正则唯一归类到一个区域；
若不能，说明协议被绕过，必须在写入点修复而非在解析侧加兜底。

## 三、执行流程

### 第 1 步 · 盘点日志写入点与解析点

- 动作：全量搜索日志格式化位置与正则解析位置，两侧都要找。
  ```bash
  grep -rn 'strftime\|log(\|print(' --include=*.py . | grep -v __pycache__
  grep -rn 'match(\|test(\|split(' --include=*.html --include=*.js .
  ```
- 判据：写入点与解析点数量均已列出，且能两两配对。
- 产出：映射表（谁写、谁读、是否共用同一格式）。
- 兜底：解析点分散在多处时，以渲染入口为准回溯上游。

### 第 2 步 · 建立协议模块

- 动作：新建 `logproto.py`，集中定义受控枚举与格式化函数。
  必含四项：受控 area 枚举、`normalize_stage()`、`format_line()`、`side_of()`。
- 判据：
  - 未知输入必须降级为受控值，不得抛异常（日志不能因格式问题中断业务）
  - 时间戳精度在模块内唯一确定，全项目只此一处
- 产出：协议模块。
- 兜底：存在历史混写格式时，在 `normalize_stage()` 内做拆分归一，保持向后兼容。

### 第 3 步 · 迁移写入点

- 动作：所有写入点改为调用协议模块，删除本地拼装逻辑。
- 判据：全项目搜索时间戳格式化调用点，业务代码中应为 0 处。
- 产出：迁移后的写入点。
- 兜底：无法改动的第三方回调，用包装函数包一层，保持调用签名不变。

### 第 4 步 · 迁移解析点

- 动作：解析侧改用与协议一致的锚定正则，并显式声明受控区域集合。
- 判据：正则以 `^` 锚定行首，禁止无锚点的 `includes()` 猜测。
- 产出：迁移后的解析点。
- 兜底：保留关键词兜底分支，但置于协议分支之后，仅处理无前缀的历史行。

### 第 5 步 · 状态判定加固

- 动作：修复由关键词猜测状态（如含某词即视为已停止）的逻辑。
  改为按行首 area 判定归属，完成标记优先级高于停止标记。
- 判据：构造「正常完成且正文含停止字样」的用例，判定结果必须为未停止。
- 产出：加固后的状态判定。
- 兜底：无法区分时以显式收尾标记为准，不做语义猜测。

### 第 6 步 · 句柄生命周期治理

- 动作：每次重新打开日志文件前，先关闭上一轮持有的句柄。
- 判据：连续执行 N 次后句柄数不增长，Windows 上表现为文件不被锁死。
- 产出：无泄漏的打开与关闭配对。
- 兜底：以 try except 包裹关闭，失败不阻断主流程。

### 第 7 步 · 建立回归测试

- 动作：编写测试，镜像解析侧正则，断言协议产出可被正确解析。
  必须覆盖：时间戳锚定、遗留格式归一、非法输入降级、区域路由、真实序列分流、状态误判回归。
- 判据：全部用例通过，且必须包含至少一个旧逻辑会失败的用例（证明测试有效）。
- 产出：可执行测试。
- 兜底：测试无法运行时，至少保留用例文档供人工核对。

## 四、输出规范

- 产出形态：协议模块、迁移后的写入与解析点、回归测试
- 落盘位置：协议模块置于被治理项目的核心层，测试置于 `tests/`
- 命名规则：模块名体现协议语义，避免 `utils.py` 这类无指向命名

## 五、边界与降级

- 信息不足时：按零依赖、向后兼容、不中断业务三条默认推进，并在结论中标注所采用的假设。
- 环境受限时（无脚本执行能力）：协议模块与测试以文件形式完整交付，
  并附逐条手工核对清单，交付完整性不因无法执行而下降。

## 六、质量自检

- [ ] 协议模块是唯一格式来源，业务代码中无第二处时间戳拼装
- [ ] 解析侧正则全部行首锚定
- [ ] 未知与非法输入降级处理，不抛异常
- [ ] 回归测试含「旧逻辑会失败」的用例
- [ ] 状态判定中完成标记优先级高于停止标记
- [ ] 日志句柄有明确的关闭路径

## 七、资源说明

- `references/` —— 协议设计原则、故障模式清单、迁移 checklist
- `scripts/` —— 协议一致性校验器，扫描并报告未迁移的写入点
- `assets/` —— 协议模块模板与回归测试模板

## 八、典型故障模式速查

| 症状 | 根因 | 处理 |
|---|---|---|
| 日志全落在一个区域 | 写入端时间戳精度与解析端正则不一致 | 统一到协议模块 |
| 正则永不匹配 | 缺 `^` 锚定，或格式含全角符号 | 加锚定，全角转半角 |
| 已完成显示为已停止 | 关键词猜测状态 | 按 area 判定，收尾标记优先 |
| 文件反复执行后打不开 | 句柄泄漏，Windows 锁文件 | 重开前先关闭 |
| 账号轨道错乱 | 无锚点正则误捕正文内容 | 行首锚定加显式捕获组 |
